# CLAUDE.md

## Architecture

This repository manages macOS dotfiles via symlinks. The `config/` directory holds the source-of-truth config files; `scripts/link.sh` creates symlinks from there to the appropriate locations. See `Makefile` for available commands.

### Key notes

- The repo also targets an omarchy (Arch Linux) machine, branching on `uname -s` in the `Makefile` and `scripts/`. There omarchy owns packages, the login shell and several config files, so a path omarchy seeded first is either replaced by the repo's file (omarchy's copy is deleted, except `~/.ssh/config`, kept as `config.omarchy.bak`) or left alone, per app. `docs/poc/omarchy4-migration/2026-10-01-status-for-omarchy-agent.md` records what is implemented, what is only decided, and the checks still owed on that machine; read it before touching the Linux side.
- On Linux, `config/packages/linux.txt` is the package list (the `Brewfile`'s counterpart) and `scripts/pkg.sh` feeds it to `omarchy pkg add` and `yay`. The repo's git config, Ghostty config and generated `~/.ssh/config` replace omarchy's; herdr and starship stay omarchy's, except that `[keys]` in herdr's file is cut down to the prefix so the bindings match the mac's. mise owns `~/.config/mise/config.toml` on both OSes, and `scripts/runtime.sh` adds runtimes with `mise use -g` instead of linking a file.
- All scripts use `set -euo pipefail` and are idempotent: they check for file/directory existence before creating links/dirs, so re-running them will not overwrite existing configurations.
- `config/git/.gitconfig`, `config/git/.gitconfig-work`, SSH config, and the work-specific zsh config (`~/.zshrc.work`, not git-managed) are copied rather than symlinked to allow local modification.
- Terminal multiplexing (panes, tabs, workspaces, copy mode) is owned by herdr, not by the terminal emulator. `config/ghostty/config.ghostty` deliberately binds no leader key and no pane/tab keys; herdr holds the prefix `ctrl+g` (`config/herdr/config.toml`). Do not re-add pane or tab bindings to the terminal config; they would shadow herdr's prefix.
- Ghostty is the terminal herdr runs on. herdr vendors Ghostty's VT engine for pane emulation, and Ghostty implements both protocols herdr depends on: the kitty keyboard protocol, and the kitty graphics virtual placeholders pane images are drawn with. Hammerspoon's Option+Space hotkey points at Ghostty.
- Reusable agent instructions live in `llm/skills/` only; there is no `llm/commands/` and no `~/.claude/commands` link. See `llm/README.md` for the skill-vs-command criterion and the current roster.
- `llm/skills/visual-pr/`, `llm/skills/retro/`, `llm/skills/writing-for-agents/`, and `llm/skills/shut-up-and-code/` are vendored from upstream repos rather than installed as plugins; `llm/upstream-skills.tsv` records the upstream commit each has been reviewed through, and `scripts/llm.sh` prints (but does not apply) a compare URL when upstream moves past it. See `llm/README.md` for why each was vendored and what the local copy changes.
- AI agent work is expected to run on top of herdr. `scripts/llm.sh` generates the herdr skill, installs herdr's Claude Code integration, and registers the related `SessionStart`/`PreToolUse` hooks (`llm/hooks/`); see its comments for the mechanics. `llm/AGENTS.md` carries the standing instruction that makes the herdr skill fire without being asked. Each hook fails open — does nothing — when it can't decide, rather than erroring.
- `scripts/llm.sh` also installs the AutoHarness plugin (`tigerless-labs/autoharness`, scope `user`) via the official marketplace rather than vendoring it — see `llm/README.md` for why. It self-learns and prunes Claude Code skills from real session work; it only ever touches skills it wrote itself.
- `config/herdr/config.toml` keeps hand-written entries limited to intentional deviations from `herdr --default-config`, so version upgrades do not turn it into a full-file diff. herdr also writes to that file itself when settings change through its UI, so machine-written keys appearing in the diff are expected rather than a mistake.
- The `Brewfile` is Ruby evaluated by `brew bundle`, so entries can be gated: a `personal` boolean at the top of the file tests for `~/.config/dotfiles/personal` (an empty, untracked marker created by `make personal`), and entries carrying `if personal` are installed only where it exists. This keeps the package list itself tracked and alphabetical while letting one checkout serve machines that install their own applications and machines where those applications are provisioned outside Homebrew. The marker's presence is the only discriminator by design: do not add logic that detects how a machine is managed, and do not move gated entries into an untracked overlay file. `brew bundle` is invoked without `--cleanup`, so a gated-off entry is skipped rather than uninstalled. Verify a change with `brew bundle list --all`, which unlike bare `brew bundle list` includes casks. The marker path is hardcoded under `$HOME` rather than `$XDG_CONFIG_HOME` because `brew bundle` scrubs the environment before evaluating the `Brewfile` (`HOME` survives, `XDG_CONFIG_HOME` arrives as `nil`), so the writing and reading sides must agree on a fixed path; `make personal` is kept out of `make all` so that a machine never opts itself in.
