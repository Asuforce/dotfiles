# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Architecture

This repository manages macOS dotfiles via symlinks. The `config/` directory holds the source-of-truth config files; `scripts/link.sh` creates symlinks from there to the appropriate locations. See `Makefile` for available commands.

All setup scripts are idempotent: they check for file/directory existence before creating symlinks or copying files, so re-running them will not overwrite existing configurations.

### Key notes

- All scripts use `set -euo pipefail` and check existence before creating links/dirs.
- Architecture detection (arm64 vs x86) determines Homebrew prefix (`/opt/homebrew` vs `/usr/local`).
- `config/git/.gitconfig` and `config/git/.gitconfig-work` are copied rather than symlinked to allow local modification; they are listed in the backup section of README.
- Files that are copied (not symlinked) allow local modification: git configs, SSH config, and work-specific zsh config (`~/.zshrc.work`, not git-managed).
- Terminal multiplexing (panes, tabs, workspaces, copy mode) is owned by herdr, not by the terminal emulator. Both `config/ghostty/config.ghostty` and `config/wezterm/wezterm.lua` deliberately bind no leader key and no pane/tab keys; herdr holds the prefix `ctrl+g` (`config/herdr/config.toml`). Do not re-add pane or tab bindings to a terminal config; they would shadow herdr's prefix.
- Ghostty is the terminal herdr is being moved onto, and WezTerm is kept alongside it until the switch is confirmed. herdr vendors Ghostty's VT engine for pane emulation, and Ghostty implements both protocols herdr depends on: the kitty keyboard protocol, and the kitty graphics Unicode virtual placeholders that pane images are drawn with (WezTerm leaves the kitty keyboard protocol off by default and implements kitty graphics without the virtual placeholders, so pane images cannot work there). `config/ghostty/config.ghostty` is a port of the WezTerm config; its only intentional visual difference is the color scheme, since Ghostty ships no Gogh variant and uses the closest built-in, `Atom One Dark`. Hammerspoon's Option+Space hotkey points at Ghostty. Once the switch is settled, drop the WezTerm cask, config, and link step.
- Reusable agent instructions live in `llm/skills/` only; there is no `llm/commands/` and no `~/.claude/commands` link. Slash commands and skills overlap in what they can express, but a skill carries a `description` that lets the model reach for it unprompted, so keeping both meant maintaining two mechanisms for one job. `apply-review`, `create-pr`, and `create-repo` moved over from commands, and `create-pr` was later replaced by the vendored `visual-pr` (below). Everything else was dropped once Claude Code shipped a built-in that already covered it, which is the standing test for whether a skill belongs here: `review-pr` because the built-in `code-review` skill takes a PR number and can post or apply its findings; `guide` because plan mode explores read-only and presents options for approval, with the `Plan` and `feature-dev:code-architect` agents for the same job in a subagent; `empirical-prompt-tuning` because `claude plugin eval` runs eval cases with LLM graders, repeated runs, and a no-plugin ablation arm, and resolves a `~/.claude/skills/<name>` directory as a target, so the evaluation lives next to the skill instead of in a hand-run procedure; `find-skills` because `/plugin` and `claude plugin install` discover and install skills without the separate `npx skills` ecosystem it assumed. `apply-review` survives that test because `code-review` generates its own findings rather than consuming a human reviewer's comments, and the `/pr-comments` command that once did is gone. Add new instructions as `llm/skills/<name>/SKILL.md`, and use `disable-model-invocation: true` for the side-effecting ones (as `create-repo` does) instead of reintroducing a command.
- `llm/skills/visual-pr/` is vendored from `humanlayer/skills` rather than installed as a plugin, and `llm/upstream-skills.tsv` records the upstream commit each vendored skill has been reviewed through. It replaces the hand-written `create-pr`. What upstream is worth taking is the discipline it imposes on a PR body: the reason for the change in exactly one sentence, one to three reviewer warnings, and a change outline built from structural views (SQL and endpoint contracts, key types, pseudocode, a shallow file tree, component trees, call and data flow) instead of prose or a file-by-file changelog. The local copy drops upstream's HumanLayer assumptions (`.humanlayer/tasks/` body paths, a cloud permalink in the report) and its bundled second copy of `show-me`, which would have drifted from `llm/skills/show-me/`; it re-adds what `create-pr` did and upstream does not (a draft PR assigned to `@me` against the detected default branch, the Jira ticket id read off the branch name, `gh pr view --web`); and it leaves a repository's own `.github/PULL_REQUEST_TEMPLATE.md` in charge of the headings when one exists, placing the structural views inside its sections rather than overwriting them with the three-section form. `create-pr`'s second template path, `${HOME}/dotfiles/.github/PULL_REQUEST_TEMPLATE.md`, was dropped rather than carried over: it has never existed on this machine. Vendoring beat `claude plugin install` because none of those deviations survive a plugin update and the plugin would write a `.humanlayer/` directory into every repository it ran in. The cost is that upstream fixes no longer arrive on their own, which is what the drift check in `scripts/llm.sh` is for: it prints a compare URL when upstream moves past the recorded commit and applies nothing, because these are prompts that have to be read before they are taken. It fails open on a missing `gh`, an unreachable network, or a missing manifest. `show-me` is listed in the manifest too, pinned past `Make show-me user-invocable` — that commit adds `disable-model-invocation: true`, which `llm/AGENTS.md` needs off, and it had already landed upstream unnoticed before the manifest existed, which is the failure the manifest is meant to make visible.
- `llm/skills/retro/` is vendored from `mattpocock/skills`, alongside `llm/skills/writing-for-agents/` as its dependency: `retro`'s first step calls the `writing-for-agents` skill for its style guide, so vendoring `retro` alone would leave that call dangling. No built-in covers this gap: the built-in `code-review` skill reviews a diff against coding standards, while `retro` reviews the session and the agent's environment itself (steering files, missing automated checks, tool economy) to suggest what should change before the next session, a different input entirely. Both ship `disable-model-invocation: true` upstream and keep it here: `retro` is genuinely user-invoked ("the user has asked for a retrospective"), and `writing-for-agents` is pulled in only to satisfy `retro`'s dependency, not for its own standing use, so neither should fire unprompted. `writing-for-agents` governs the structure of agent-facing documents (context pointers, information hierarchy, leading words); it doesn't overlap `show-me`, which governs visuals inside those documents. Upstream's `writing-for-agents/agents/openai.yaml` was dropped as an OpenAI-format export, the same call `visual-pr` makes dropping upstream's bundled second `show-me`. `retro` lives in upstream's `skills/in-progress/`, so its manifest entry is expected to drift more often than the others.
- AI agent work is expected to run on top of herdr. `scripts/llm.sh` regenerates `llm/skills/herdr/SKILL.md` from `herdr --skill` on every run (git-ignored, so herdr upgrades do not show up as diffs) and installs herdr's Claude Code integration hook with `herdr integration install claude`, which registers a `SessionStart` hook in `~/.claude/settings.json` so herdr can read the agent's working/idle/blocked/done state. `llm/AGENTS.md` carries the standing instruction that makes the herdr skill fire without being asked for each time, and names the concrete triggers (Agent tool, second agent, waiting on one) plus the Japanese phrasings for them, because an abstract "default substrate" rule is not recognizable at the moment the model decides whether to delegate. The generated skill's `description` is rewritten by `scripts/llm.sh` right after generation: herdr ships it gated on the user naming herdr in the prompt, and since the description is the only part of a skill the model reads while routing, that gate silently cancelled the standing instruction. Only that line is replaced; the generated body is left alone, so the override survives herdr upgrades. All herdr steps are skipped when the `herdr` binary is absent.
- `llm/hooks/herdr-repo-workspace.sh` is a second `SessionStart` hook that keeps herdr at "one repository = one workspace = side-by-side worktrees": on startup it moves the calling pane into the existing workspace for the same repository, keeps the panes in a single row (at most 3 columns, at least 50 columns wide each) and labels worktree panes and agents with the branch name. Repository identity comes from the shared `.git`, so a linked worktree groups with its main checkout. Unlike the herdr-owned hook, it lives in this repository: `scripts/llm.sh` symlinks it into `~/.claude/hooks/` and merges its registration into `~/.claude/settings.json` with `jq`, because `llm/settings.json` is only copied onto a machine that has no `~/.claude/settings.json` yet. The hook fails open — it prints nothing and leaves the layout alone whenever it cannot decide. Adapted from https://zenn.dev/gemcook/articles/herdr-worktree-parallel.
- `llm/skills/shut-up-and-code/` is vendored from `chl03ks/shut-up-and-code` for the same reason `visual-pr` exists: a `CLAUDE.md` line asking for comment restraint does not reliably stop the model from narrating code back to the user in comments (a known failure mode, cited in upstream's README against anthropics/claude-code#65961), because a skill loads as a document at the point the model decides how to write, where a config line competes for attention with everything else. The skill alone still depends on the model choosing to invoke it, so two hooks vendored alongside it from the same repo's `hooks/` directory force the ruleset into context instead: `llm/hooks/shut-up-and-code-always-on.sh` (`SessionStart`, `startup|resume|clear|compact`) injects the skill body, and `llm/hooks/shut-up-and-code-audit-on-commit.sh` (`PreToolUse`, `Bash`, matching a `git commit` in the command) re-injects the self-audit reminder right before a commit lands, since a long session can scroll the initial injection out of relevance. Both are gated on `~/.claude/.shut-up-and-code-always` (upstream's own opt-out mechanism: delete the file to disable, recreate it to re-enable) rather than always firing unconditionally, so the existing "say `normal comments` to turn it off for this session" escape hatch still works. `scripts/llm.sh` symlinks both hooks into `~/.claude/hooks/`, merges their registration into `~/.claude/settings.json` with `jq` for the same reason `herdr-repo-workspace.sh` does, and creates the flag file if absent so a fresh machine gets always-on by default. `llm/upstream-skills.tsv` tracks the skill and the `hooks/` directory as two separate rows against the same repo, since they can drift independently.
- `config/herdr/config.toml` keeps hand-written entries limited to intentional deviations from `herdr --default-config`, so version upgrades do not turn it into a full-file diff. herdr also writes to that file itself when settings change through its UI, so machine-written keys appearing in the diff are expected rather than a mistake.
- The `Brewfile` is Ruby evaluated by `brew bundle`, so entries can be gated: a `personal` boolean at the top of the file tests for `~/.config/dotfiles/personal` (an empty, untracked marker created by `make personal`), and entries carrying `if personal` are installed only where it exists. This keeps the package list itself tracked and alphabetical while letting one checkout serve machines that install their own applications and machines where those applications are provisioned outside Homebrew. The marker's presence is the only discriminator by design: do not add logic that detects how a machine is managed, and do not move gated entries into an untracked overlay file. `brew bundle` is invoked without `--cleanup`, so a gated-off entry is skipped rather than uninstalled. Verify a change with `brew bundle list --all`, which unlike bare `brew bundle list` includes casks. The marker path is hardcoded under `$HOME` rather than `$XDG_CONFIG_HOME` because `brew bundle` scrubs the environment before evaluating the `Brewfile` (`HOME` survives, `XDG_CONFIG_HOME` arrives as `nil`), so the writing and reading sides must agree on a fixed path; `make personal` is kept out of `make all` so that a machine never opts itself in.
