# visual-pr

現在のタスクに対応する PR を作成または更新し、レビュアーが「なぜこの変更があるのか」と「実装の形」を掴める本文を書く。

本文の型は `references/pr_description_template.md` にある。必ず読み、その型を超えて本文を膨らませない。

図の描き方は `show-me` スキルに従う。PR 本文に HTML は置けないので、Mermaid・ファイルツリー・コールツリー・擬似コード・`diff` のテキストビューだけを使う。

## Phase 1: PR の特定

現在のブランチに PR があるか確認する。

```bash
gh pr view --json url,number,title,state,baseRefName,headRefName 2>/dev/null
```

- 見つかれば更新モード。その PR の本文を書き直す。
- 見つからなければ作成モード。`git status --short --branch` で未コミットの変更を確認し、タスクに関係するものだけをコミットする。
- 現在のブランチにタスクの作業がなく、安全に作れる PR もない場合にだけ、対象の PR をユーザーに選んでもらう。

## Phase 2: コンテキスト収集

### Jira チケット ID の取得

ブランチ名の最初のセグメント（`/` 区切り）を Jira チケット ID として使用する。

```bash
git branch --show-current | cut -d'/' -f1
```

取得できない場合やブランチ名に `/` が含まれない場合は、Jira チケット ID なしで進める。

### デフォルトブランチの特定

```bash
git symbolic-ref refs/remotes/origin/HEAD | sed 's|refs/remotes/origin/||'
```

取得できない場合は `main` にフォールバックする。取得した値を以降の手順で `$DEFAULT_BRANCH` として使用する。

### 変更内容の把握

```bash
git log $DEFAULT_BRANCH...HEAD --oneline
git diff $DEFAULT_BRANCH...HEAD
```

diff は全部読む。挙動と責務の所在が分かるところまで周辺のコードも読む。チケットや関連ドキュメントがあれば併せて読む。

### PRテンプレートの読み込み

`.github/PULL_REQUEST_TEMPLATE.md`（小文字の `.github/pull_request_template.md` も見る）があれば読み込む。なければスキップする。

### 手本PRの確認（引数指定時のみ）

引数としてPR番号が指定されている場合のみ実行する。

```bash
gh pr view $ARGUMENT
```

## Phase 3: 本文を書く

`references/pr_description_template.md` を読んでから書く。

### リポジトリのテンプレートがある場合

テンプレートの見出し構造をそのまま使う。3節の型で上書きしない。各節には次の対応で内容を入れる。

- 背景・目的にあたる節: 「なぜ」を1文で
- 変更内容にあたる節: 構造ビュー。ファイル別の変更履歴を書き下さない
- レビュー観点にあたる節: 注意してほしいこと1〜3項目

### リポジトリのテンプレートがない場合

`references/pr_description_template.md` の3節をそのまま使う。

### 構造ビューの選び方

その PR の説明に効くビューだけを、一番分かりやすい順に並べる。変わっていないカテゴリの節は作らない。

- SQL のテーブル定義・主要なカラムと関連、エンドポイントのリクエスト/レスポンス契約
- 実装の鍵になるデータ構造や型の変更
- 業務ロジックの擬似コード
- 変更された責務が分かる浅いファイルツリー
- React のコンポーネントツリー、重要な hooks・state・パッケージ境界
- コールツリー、コールスタック、制御フロー、データフロー

既存の形に対する変更は ```diff で示す。大半が新規の場合、または diff 記法だと責務や順序が読み取りにくくなる場合は、完成形をそのまま出す。

### 文体

- 人が人に宛てて書く。専門用語や俗語を避け、簡潔で筋の通った文にする
- 技術文書調ではなく、チームへの連絡に近い会話調で書く。箇条書きや太字の多用を避ける
- diff を見れば分かる情報（クラス名・関数名・具体的な値）は本文に書かない
- 実行していない検証を実行したように書かない。どこまでやったかを明示する
- 一連の作業を複数PRに分けている場合は、この PR が担当する範囲と先行 PR に任せた範囲を1文ずつで切り分ける

### タイトル

- Jira チケット ID が取得できた場合: `[PROJ-123] 変更内容を端的に表すタイトル`
- 取得できなかった場合: `変更内容を端的に表すタイトル`
- コミット群全体を俯瞰した変更の目的を1文で表現する。実装の詳細ではなく「何を達成するか」を書く
- 言語はリポジトリのコミットメッセージの慣習に合わせる

## Phase 4: PR への反映

本文は一時ファイルに書き、`--body-file` で渡す。リポジトリ内に作業ファイルを残さない。

```bash
body="$(mktemp)"
```

### 作成モード

ブランチが origin に push されていなければ先に push する。

```bash
git push -u origin $(git branch --show-current)
gh pr create \
  --draft \
  --assignee @me \
  --base "$DEFAULT_BRANCH" \
  --title "[<Jira チケット ID>] <タイトル>" \
  --body-file "$body"
```

### 更新モード

```bash
gh pr edit <number> --body-file "$body"
```

どちらの場合も、反映が成功したことを確認してから `rm -f "$body"` する。

## Phase 5: 確認と報告

作成したPRをブラウザで開く。

```bash
gh pr view --web
```

`references/describe_pr_final_answer.md` の型で報告する。
